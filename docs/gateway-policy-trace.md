# 内置策略表达式与调用 Trace

日期：2026-11-04。已实现内置规则集 `legal-basic-2`、虚构正反例测试、请求级 Trace 和后台访问入口。回填不在本次范围。

## 策略不是只有一个正则

完整规则包含：规则 ID、匹配表达式/识别器、补充校验、作用方向、处理动作和替换格式。

例如手机号：

```text
规则 ID：builtin.phone
匹配：(?<![0-9])(?:\+86[ -]?)?1[3-9][0-9][ -]?[0-9]{4}[ -]?[0-9]{4}(?![0-9])
校验边界：中国大陆手机号格式，不验证号码真实归属
请求动作：REDACT，替换后重新检测
回答动作：出现未脱敏手机号则 BLOCK
替换结果：<PHONE_001>、<PHONE_002> …
```

“11 位”是号码主体长度，不表示任意 11 位数字都是手机号；正则中的数字范围、边界和可选分隔符负责候选匹配。`<PHONE_001>` 是识别后的替代标识，不是正则通配符。

身份证沿用共享格式规则，增加有效日期与校验位验证，类型为 `ID_NUMBER`，替代标识为 `<ID_NUMBER_001>`；尚不验证行政区代码是否存在，也不覆盖旧式 15 位证件。银行卡当前是格式候选规则，尚未通过 Luhn/发卡行校验，可能误报。

邮箱、案号、合同编号等内置规则与私钥/sk- 凭据阻断规则也展示在后台。姓名、机构等由 HaS/Presidio/规则合并，不能仅靠数字正则保证识别。BLOCK 优先；未命中且所有必选检查成功，才能 ALLOW。

内置规则直接参与网关请求和回答检测，不是仅展示用的文档。即使语义检测器没有返回手机号，内置手机号规则仍会处理。相同原值在同一次请求内保持占位符一致；不同写法的号码尚无统一规范化，不承诺跨会话稳定编号。

## 页面入口和单元测试

打开 `http://127.0.0.1:8787/admin`，登录后进入“内置策略与测试”。

页面显示实际代码中的表达式、校验边界、请求/回答动作和占位符。点击“运行内置虚构样例”运行 11 个固定正反例：普通手机号、+86/分隔符手机号、错误前缀、长数字边界、身份证校验位、无效日期、邮箱、私钥和普通文本。

测试只执行内置格式规则，不调用上游模型、不接收任意真实材料、不修改线上规则。页面展示虚构输入及替换结果。每行断言针对指定规则；例如身份证校验失败不代表整个请求会 ALLOW，其他规则仍可能将其视为银行卡候选。不将这些单元测试成绩当作 HaS 真实材料召回率。

表达式仍由代码维护；请求/回答动作现已支持管理员编辑、草稿测试、不可变发布、Channel 显式启用和回滚，见 [完整操作与验收](gateway-policy-workflow.md)。上面的 11 个例子展示基线规则；发布门槛额外运行各类型动作与强制阻断断言，共 45 个。未提供任意表达式编辑或自动灰度。

## Trace 放在哪里

后台“调用审计 / Trace”列表中，每个已鉴权并进入审计的聊天请求都有 Trace 按钮。点击展开这一轮的执行步骤。实时虚构模型测试完成后也会自动展开对应 Trace。

```mermaid
flowchart LR
    A[身份与 Channel 权限] --> B[请求结构与模型授权]
    B --> C[凭据规则 / 识别 / 假名化 / 复检]
    C --> D[发送前再次授权]
    D --> E[LiteLLM 调用指定模型]
    E --> F[回答敏感信息检查]
    F --> G[返回前授权 / 审计 / 交付回答]
```

| 阶段 | 展示内容 |
|---|---|
| authorization | Channel ID、实际策略版本、权限检查状态 |
| request.validation | 消息角色、各消息字符数、请求字节数、非流式标记 |
| request.policy | 命中内置规则 ID、合并后的实体类型/数量、ALLOW/REDACT/BLOCK、复检结果 |
| upstream.authorization | Key、用户、通道、授权是否仍有效 |
| upstream.call | 目标路由、客户端模型别名、上游模型名称、单次调用耗时、回答长度、可得的 finish_reason/token 用量 |
| response.policy | 固定策略版本、回答命中规则、检测/脱敏计数、实际动作及 PASS/BLOCK/ERROR |
| response.release | chat.completion 结构、assistant 角色、返回前检查；不留存正文 |

每个阶段有开始时间、状态及毫秒耗时。未走到上游时没有上游阶段；调用报错时不推断“上游绝对没有收到”，只有成功返回才能证明收到完整回答。RUNNING/PENDING 表示尚未完成或异常中断，不能当作通过。Token 用量只记录上游实际提供的整数，没有就留空，不估算。

这对应会议中逐步查看请求/回答的 Trace 思路，但当前只追踪网关可观察的 API 步骤，不是模型内部思维过程，也不是宿主 Agent 的完整工具执行日志。当前不支持 tools、流式和 Responses API，所以不会伪造工具调用记录；多轮会话/案件级 Trace 关联仍待实现。

## Response 的内容在哪里

真正的 API 回答结构仍是：

```json
{
  "object": "chat.completion",
  "model": "privacyguard-local",
  "choices": [{"index": 0, "message": {"role": "assistant", "content": "经过回答复检的内容"}, "finish_reason": "stop"}],
  "privacyguard": {"status": "approved", "request_id": "与 Trace 相同的 ID", "entity_count": 2}
}
```

上例是结构说明。阻断时返回 `error.code` 和 `request_id`，不附带被拦截的模型原始回答。

后台虚构测试的实际回答会在“本次通过复检的模型回答”区域临时展示，隐藏 Key、退出或刷新后消失；不保存到 Trace 数据库。历史 Trace 保存角色、长度、规则动作与结果结构，不留原文、完整脱敏正文、密钥或映射，避免将日志库变成新的客户材料库。完整生产正文回看不在当前实现范围。

## 隔离、故障与限制

- Trace 读取要求独立管理员会话，并按组织归属检查；未知或跨组织请求拒绝，不通过调用 Key 提供后台访问。
- 不记录异常字符串、HTTP Authorization、模型原始请求/回答。Trace 存储失败时阻断请求或回答交付，不绕过审计。
- 尚未通过鉴权或因限流未进入审计的请求，没有业务 Trace；旧历史记录无分阶段数据时显示暂无记录。
- 当前保存本机请求级元数据，自动保留期/清理和大规模检索尚未实现。
