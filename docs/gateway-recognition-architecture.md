# 识别管道技术路线：MCP 与 Gateway 的共同核心

核对日期：2026-11-04。本页描述实际代码，不将设计目标当作已实现能力。总图位于 README 的“管道如何识别”部分；策略操作流程见 `gateway-policy-workflow.md`。

## 识别模型与策略各做什么

| 组件 | 职责 | 当前默认链路 |
|---|---|---|
| RedactionEverything | 解析文件、调用 OCR、调用 HaS NER | 本机 `:8000`；网关通过适配器提交文本窗口 |
| PaddleOCR / 结构识别 | 将扫描页转为文本 | 文件路径需要时使用；不参与普通网关文本请求 |
| HaS 0.6B | 按识别服务的实体类型定义找出语义实体及位置 | 默认语义检测器，本机 `:8080`；不是最终合同分析模型 |
| 共享格式规则 | 找手机号、邮箱、证件等结构化候选 | 与 HaS 结果合并；不能替代姓名、机构等语义识别 |
| Presidio | 补充检测，参与输入及复检 | 本机 `:5002`；必须成功，失败闭锁 |
| 可选 MLX NER | 额外语义检测结果 | 默认关闭；显式启用但缺配置或执行失败时阻断 |
| PrivacyGuard | 校验识别结果、合并、统一占位符、复检与调度 | MCP 与网关共享检测核心，执行边界各自独立 |
| Gateway 策略版本 | 决定实体的请求/回答动作 | 默认请求 REDACT、回答 BLOCK；可按类型编辑、测试后发布 |
| LiteLLM | 将获准消息发送给已配置模型 | 不替代检测器，也不自动接管宿主 Agent 流量 |
| MLX/Qwen3 1.7B | 对获准内容生成分析回答 | 当前本机 `:8011/v1`；输出还需检查后才能交付 |

这里的端口是已有本机部署约定，不表示新机器上的服务已经启动。当前 HaS 型号依据仓库内既有真实链路验收及配套服务配置；不代表管理员可在后台自由切换识别模型。

“预设实体”是类别和识别规则，例如 PERSON、ORGANIZATION、ADDRESS、PHONE、EMAIL、ID_NUMBER，不是预先把所有真实人名列成词典。HaS 根据上下文预测实体；规则根据格式匹配；Presidio 补充识别。输出含类型、起止位置、置信度和来源。当前动作编辑器不会修改 HaS 的识别提示词或实体类型配置，更不会把没有配置动作的类型排除出扫描。

## 一次网关请求的真实顺序

1. 检查调用 Key、用户、Channel、模型别名、输入字段和大小；固定本次不可变策略快照。
2. 检查私钥/sk- 等强制阻断项、客户端伪造占位符。
3. `PrivacyGuard.detect` 调用 `SemanticEnsemble.analyze`。文本按 2400 字符窗口、300 字符重叠交给 RedactionEverything/HaS；校验返回原值和区间一致，再加入共享规则、分块 Presidio 结果，扩展同值重复实体并合并重叠区间。
4. 网关 `Protection` 叠加内置格式规则，验证类型、位置和置信度。当前不确定语义类型集合包含 PROJECT、ORGANIZATION、ADDRESS、DEPARTMENT、COURT、LAW_FIRM，置信度低于 0.85 时阻断；PERSON 暂不在此阈值集合中，不能把它表述为所有低置信度姓名均会阻断。
5. 对候选应用本次策略：命中 BLOCK 就停止；REDACT 由 PrivacyGuard 生成 `<PERSON_001>`、`<PHONE_001>` 等。单请求内同类型同原值复用映射，不回填原值。
6. 遮蔽已登记的占位符后，再次运行完整检测核心；凭据、未知占位符或残留命中仍阻断。发送前重新检查授权并写审计，成功才调用 LiteLLM。
7. 对模型回答应用同一版本的回答策略：默认 BLOCK，可配置 REDACT 后复检；只有通过最终授权和审计才能返回。

窗口识别在当前实现中是顺序执行，不宣称模型并行扫描。`analyze_text` 适配器当前通过本机临时 TXT → RedactionEverything 上传/解析/NER 完成窗口识别，而不是一个无状态纯内存接口；后端上传区可能保留材料，需要另设清理和访问控制。

重叠候选在共享检测核心中已经合并，网关对收到的候选及额外内置规则在再次合并前检查 BLOCK。它不能恢复共享核心合并时已经丢弃的其他类型标签。对所有原始多类型候选保留来源并做全局 BLOCK 优先，是后续需要加强的识别冲突治理；当前不声称已完整解决所有跨检测器标签冲突。

## 与 MCP 相同和不同的地方

两者调用同一 `PrivacyGuard.detect`，不是另外做了一套只有正则的网关。MCP 先处理文件格式、OCR 和安全引用，再走受控问答；网关接收已经是文本的 API 消息，增加用户/Channel 权限、策略版本和请求 Trace。两条入口不会默认重复串联，现有 MCP 请求也不自动经过网关。

网关当前拒绝文件、图片、多模态、tools、streaming 和 Responses API。不应让客户端把“本地文件路径”当作网关已读取文件的证据；文件必须走已经验收的 MCP 文件处理入口。下载安全文件时才进入独立副本构建、结构检查及原值残留验证。

## 怎么证明管道确实执行了脱敏

| 安全条件 | 实现 / 验收证据 | 不能据此推断 |
|---|---|---|
| 未批准内容不发分析模型 | 记录型 HTTP 上游测试实际出站体无虚构邮箱、手机号；私钥阻断时收到零请求 | 识别服务不接触原文 |
| 必须经过模型识别与补充检测 | 默认注入 `core.detect`，其调用 HaS、规则和 Presidio；依赖异常阻断 | 所有真实实体必然被识别 |
| 草稿不能悄悄上线 | 修订号、测试摘要、不可变版本、显式通道绑定及回滚测试 | 完整模型权重依赖已固定 |
| 回答不能直接穿透 | 回答策略、残留检查、未知占位符和授权复核 | 回答事实和法律观点必然正确 |
| 可以追溯执行 | 七阶段 Trace，版本、动作、计数、耗时、错误码；真实浏览器启用/回滚验收 | Trace 是模型内部思维或原文存档 |

现有回归结果：105 项测试、12 个子测试通过，真实浏览器完成识别/假名化/模型回答、新策略请求阻断以及回滚后恢复。45 个发布断言是固定虚构规则与动作测试，不是每次发布都跑真实 HaS，也不是中文语义召回率评估。

可定位代码：`privacyguard/gateway/app.py`、`privacyguard/core.py`、`privacyguard/semantic.py`、`privacyguard/adapters/redaction_everything.py`、`privacyguard/adapters/presidio.py`、`privacyguard/gateway/policies.py`、`privacyguard/gateway/policy_versions.py`。对应测试为 `tests/test_gateway.py`、`tests/test_gateway_policy_trace.py`、`tests/test_gateway_policy_versions.py`，浏览器验收为 `scripts/gateway_admin_browser.mjs`。
